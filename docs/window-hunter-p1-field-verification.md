## 三、决定性判定：真实业务流量能搭上乐观窗口

### 方法

把账号**绑定到一个它从未见过的出口**（该出口对账号的第一发请求 = 窗口起点），
然后立刻发真实业务流量，看返回满血还是降智。
全程只发 1 发/出口，避免探测即污染。

### 结论

- 乐观窗口**确实可被真实业务流量利用**【实测】：账号绑定到未见出口后，
  首发真实请求即满血。
- 适用范围：**必须先绑定后发流量**（第 3 节方法），而不是"先探测确认再发流量"——
  探测本身就是那一发首发请求，会消耗掉窗口。
- 与 P2 判定（`docs/window-hunter-ws-survival-verdict.md`）一致：窗口是**一次性资源**，
  必须在命中瞬间承接业务，不能囤积。

## 四、必须记录的测量陷阱：同一出口同一请求体，判定会波动

在"已知降智"出口（proxy 19，02:45 用过）上，用**完全相同的请求体连打 5 次**：

```
#1 石破茂   #2 高市早苗   #3 石破茂   #4 石破茂   #5 石破茂
```

同一出口、同一 prompt、同一 `cached_tokens=3840`，5 发里有 1 发给出满血。
这解释了两件事：

1. **单发判定不可信**：任何"这个出口是满血/降智"的结论都必须多发达成一致，
   或配合 `account_node_health` 的状态机（它记录了探测时刻与答案）。
2. **sub2api 的探针/采样存在假阳性风险**：`window_probe` 单发判定会把这种波动
   记为 `full_power`，进而错误地把窗口时钟重置。这对猎手的"命中即停"是实质威胁——
   可能在一个实际已降智的节点上停下来。

**建议的改进方向**（未实施，留给后续）：
- 探针命中判定改为「连续 2 发一致」或「命中后追加 1 发确认」（代价：多 ~25 token）；
- 或在 `account_node_health` 里增加 `confidence` 维度，把单发命中标为待确认。

### 附：另一个必须避免的测量陷阱

- **codex CLI 带 `tools.web_search` 时，答案可能来自联网检索而非模型知识**，
  不能作为满血/降智判据。本次验证中，`-c 'tools.web_search=false'` 与默认配置
  在**同一出口**上都返回满血，所以 codex 那 9/9 是可信的；但单看 codex 输出无法
  排除检索污染，必须配合"HTTP 极简请求（无 tools、无检索）"的对照。
- 判据的纯净形态：`POST /v1/responses`，`stream:false`，**只带短 `instructions`**，
  `input` 只问首脑问题。带长 `instructions`（如 codex 的 21KB 系统提示）会命中
  prompt cache（`cached_tokens=3840`），响应里的 `instructions` 字段会被缓存版覆盖，
  造成形态混淆。
